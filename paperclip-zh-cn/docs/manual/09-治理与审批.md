# 第 09 章　治理与审批

> 英文原文：`docs/guides/board-operator/approvals.md`、`docs/guides/board-operator/activity-log.md`、
> `docs/guides/execution-policy.md`、`doc/MCP-ACCESS-GOVERNANCE.md`、`doc/UNTRUSTED-PR-REVIEW.md`。

## 9.1 审批类型

| 类型 | 触发者 | 内容 |
| --- | --- | --- |
| **招聘 Agent**（`hire_agent`） | 通常是管理者或 CEO | 拟聘 Agent 的名称、角色、能力、适配器配置、预算 |
| **CEO 战略** | CEO | 初始战略方案；**未获批前 CEO 不能把任务推进到 `in_progress`** |
| **董事会审批**（`request_board_approval`） | 任意 Agent | 花钱、对外承诺等需要人点头的动作 |

## 9.2 审批工作流

```
pending ──→ approved
        ├─→ rejected
        └─→ revision_requested ──→ resubmitted ──→ pending
```

1. Agent 创建审批请求；
2. 它出现在 UI 的 Approvals 页审批队列；
3. 你审阅请求详情与它关联的任务；
4. 三个动作：**批准 / 驳回 / 要求修改**。

CLI：

```bash
paperclipai approvals list --company-id <id>
paperclipai approvals get <approval-id>
paperclipai approvals create --company-id <id> --type request_board_approval --payload-file payload.json
paperclipai approvals approve <approval-id>
paperclipai approvals reject <approval-id>
paperclipai approvals request-revision <approval-id>
paperclipai approvals resubmit <approval-id>
```

Agent 主动发起董事会审批（示例）：

```json
POST /api/companies/{companyId}/approvals
{
  "type": "request_board_approval",
  "requestedByAgentId": "<agent-id>",
  "issueIds": ["<issue-id>"],
  "payload": {
    "title": "批准每月托管支出",
    "summary": "预计每月 42 美元，使用 provider X。",
    "recommendedAction": "批准 provider X 并继续搭建。",
    "risks": ["用量增长可能推高成本。"]
  }
}
```

审批通过后，Paperclip 会用 `PAPERCLIP_APPROVAL_ID` / `PAPERCLIP_APPROVAL_STATUS` 唤醒申请者。

## 9.3 执行策略（execution policy）

审批不止于「一次性动作」，还可以挂到任务生命周期上：
一条任务可以被配置为必须经过**评审 / 审批阶段**才允许完成。

- 阶段类型涵盖评审与审批；
- 每一步有当前参与者（`currentParticipant`）、退回目标（`returnAssignee`）、
  上次决策结果（`lastDecisionOutcome`）；
- **通过**：`PATCH /api/issues/{id}` 提交 `{"status":"done","comment":"Approved: ..."}`；
  若还有后续阶段，Paperclip 会保持在 `in_review` 并自动转交下一位参与者；
- **要求修改**：`{"status":"in_progress","comment":"Changes requested: ..."}`，
  Paperclip 记录为 changes-requested 并退回给 `returnAssignee`；
- **不是你的阶段就别试**：其他 actor 提交会被 `422` 拒绝。

## 9.4 线程内交互卡片

比「用 markdown 问一句要不要」更可靠的方式是**结构化交互卡片**：

| 类型 | 适用 |
| --- | --- |
| `request_confirmation` | 单个是/否决策，绑定某个目标（如接受计划修订、批准上线） |
| `request_checkbox_confirmation` | 从已知清单里勾选任意子集后确认/驳回 |
| `request_item_verdicts` | 对每个条目单独批准/驳回/延后 |
| `ask_user_questions` | 少量结构化问答（选择项、文本） |
| `suggest_tasks` | 提议具体任务，被接受后变成真子任务 |

通用语义：

- **解析人范围（resolverPolicy）**：默认 `anyone`（看板或公司内任意 Agent，包括你）。
  需要限制时用 `not_creator`、`human_only` 或指定 `addresseeAgentId`；
  限制只会**收窄**，不会被公司上限放宽。
- **续跑策略**：`request_confirmation` 默认 `none`（不唤醒），
  需要恢复时显式设 `wake_assignee` 或 `wake_assignee_on_accept`。
- **目标绑定与过期**：绑定了 `issue_document` 修订的卡片，在新修订落地时
  以 `stale_target` 过期，需针对最新修订重建。
- **用户评论可覆盖**：`supersedeOnUserComment` 默认 true，
  用户评论会让待确认卡片以 `superseded_by_comment` 取消。
- **幂等**：`idempotencyKey` 用 `confirmation:{issueId}:plan:{revisionId}` 这类确定性键，
  重试不会堆出重复卡片。
- **撤回与终态过期**：创建者/当前负责人/看板用户可撤回；
  任务置 `done`/`cancelled` 会以 `issue_closed` 过期所有待处理卡片。

发起确认（示例）：

```json
POST /api/issues/{issueId}/interactions
{
  "kind": "request_confirmation",
  "idempotencyKey": "confirmation:{issueId}:plan:{revisionId}",
  "title": "确认按此计划实施？",
  "summary": "计划已更新到修订版，等待确认后拆分子任务。",
  "continuationPolicy": "wake_assignee",
  "payload": {
    "version": 1,
    "prompt": "是否批准该计划？",
    "target": { "type": "issue_document", "issueId": "{issueId}", "key": "plan", "revisionId": "{rev}" }
  }
}
```

随后把任务置为 `in_review` 并带上 `reviewInteractionId`，
这就构成了一条**真实的等待路径**。

## 9.5 董事会越权能力（Board Override）

作为看板用户，你可以随时：

- 暂停 / 恢复任意 Agent；
- 终止任意 Agent（**不可逆**）；
- 把任意任务改派给别的 Agent；
- 覆盖预算限制；
- 直接创建 Agent（绕过审批流程）。

> 「发回给我」的处理：用户说「我来审」时，把任务
> `assigneeAgentId: null` + `assigneeUserId: <user-id>`，状态置 `in_review`（不要置 `done`）。

## 9.6 活动日志与审计

被记录的活动包括：**所有写操作**、心跳状态变化、成本事件、审批、评论、work product、密钥读取。

```bash
paperclipai activity list --company-id <id>
```

UI：任意实体右侧的 Activity 面板，以及公司级活动页。

排障口诀：**任何「它为什么这么做」的问题，答案都在活动日志里**——
谁、什么时候、改了什么、关联哪条任务。

## 9.7 受治理的外部能力（MCP / 工具网关）

部分 MCP 工具被配置为 **ask first**（调用前先问）：

1. Paperclip 在你签出的任务上发一张审批卡，返回 `approval_required`；
   **不要在卡片待处理时重复调用**；
2. 批准后 Paperclip 会**按存储的、已签名的参数只执行一次**；
   唤醒里若说已执行，直接用结果，**不要再调一次**；
3. 驳回则动作没有发生，不要重试同一调用；
4. 审批 60 分钟过期，过期后重新调用即可开一张新卡；
   相同参数的重复调用是幂等的，不会堆卡片；
5. 若返回 `approval_path_missing`，说明 MCP 会话没挂在已签出的任务上，
   请在已签出该任务的运行里重试。

> 拿到任何凭据（用户粘贴、OAuth 回流、邮件、SaaS 导出……），
> **立刻**用 `POST /api/agents/me/secret-proposals` 提案为 Paperclip 密钥，
> 绝不要写进评论、文档、文件、任务描述或任何转录内容。
