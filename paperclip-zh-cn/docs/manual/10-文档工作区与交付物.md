## 10.1 三类"文档"

| 类型 | 用途 | 存放 |
| --- | --- | --- |
| **任务文档** | 单条任务的计划/报告，带修订历史 | `issue_documents`（如 `plan` 键） |
| **仓库文档** | 长期工程文档 | 本仓库 `docs/` 与 `doc/` |
| **外部文档** | 第三方手册、供应商文档 | 外部站点，本手册只引用不复制 |

任务文档支持**修订 + 目标绑定**：

```bash
# 读当前修订
GET /api/issues/{issueId}/documents/plan
# → { body, latestRevisionId, ... }

# 更新（必须带 baseRevisionId，否则 409）
PUT /api/issues/{issueId}/documents/plan
{ "title": "Plan", "format": "markdown", "body": "…", "baseRevisionId": "<latestRevisionId>" }
```

约定：计划类内容放 `plan` 文档，**不要再往任务描述里堆长计划**。

## 10.2 项目工作区 vs 执行工作区

| 概念 | 含义 | 生命周期 |
| --- | --- | --- |
| **项目工作区**（project workspace） | 项目根目录，通常是仓库 clone 或 bind mount | 长期 |
| **执行工作区**（execution workspace） | 单条任务的隔离环境：git worktree、operator 分支 | 随任务 |

规则：

- 子任务**自动继承**父任务的执行工作区；
- 非子任务的后续工作要显式传 `inheritExecutionWorkspaceFromIssueId` 才能续用；
- 私有仓库与「仅仓库」型项目工作区有专门处理；
- 跨运行持久化遵循「无远端 git 契约」：不要依赖把本地提交推回去。

## 10.3 运行时服务

需要浏览器 QA 或预览 URL 时，**用工作区的运行时控制**：

```bash
GET  /api/execution-workspaces/{id}
POST /api/execution-workspaces/{id}/runtime-services/start
POST /api/execution-workspaces/{id}/runtime-services/stop
GET  /api/execution-workspaces/{id}/runtime-services
```

要点：

- **惰性供给**：无人访问不占资源；
- 浏览器可达的 origin 与 OAuth QA 有关，跨域配置不当会导致授权回调失败；
- 运行时服务是 work product 的一种（`runtime_service`），要在任务上登记。

## 10.4 交付物：附件 + work product

**附件**是文件，**work product**是「可检查的产物指针」。两者一起构成验收证据。

```bash
# 上传
curl -X POST "$PAPERCLIP_API_BASE/api/companies/$COMPANY/issues/$ISSUE/attachments" \
  -H "Authorization: Bearer $PAPERCLIP_API_KEY" -F file=@report.pdf
# 列出 / 取内容 / 删除
curl "$PAPERCLIP_API_BASE/api/issues/$ISSUE/attachments"
curl "$PAPERCLIP_API_BASE/api/attachments/$ID/content"
curl -X DELETE "$PAPERCLIP_API_BASE/api/attachments/$ID"
```

work product 类型：

| 类型 | 用于 |
| --- | --- |
| `pull_request` | 已开 PR |
| `preview_url` | 已发布预览 |
| `runtime_service` | 托管的预览/开发服务 |
| `commit` | 值得记录的重要提交 |
| `branch` | 分支本身就是交接物 |

> 🔴 **只写在本地路径或评论里是不够的**：看板用户、评审者、云端运维可能打不开你的工作区。
> 必须上传真实交付物并登记 work product。
> 如果文件必须留在项目/执行工作区，用 `metadata.resourceRef.kind: "workspace_file"` 标注，
> 让看板能从任务打开。

## 10.5 从任务到验收的推荐节奏

1. Agent 在 `in_progress` 干活，持续把证据追加为附件与 work product；
2. 需要人看界面时，起运行时服务并登记 `preview_url`；
3. 改完发 PR，登记 `pull_request`，把 PR 链接写进评论；
4. 置 `in_review` 并挂上评审路径（确认卡片 / 审批 / 指定评审者）；
5. 合并并验证后置 `done`，必要时归档收件箱。

## 10.6 验收标准怎么写

| 弱 | 强 |
| --- | --- |
| "修一下登录问题" | "复现：POST /api/auth/login 缺 `email` 字段返回 400。验收：该字段缺失时返回 422，错误体含 `field: email`，并补一条回归测试。" |
| "优化页面" | "首屏 LCP < 2.0s（本地 throttling 档位），并给出前后对比截图作为附件。" |
