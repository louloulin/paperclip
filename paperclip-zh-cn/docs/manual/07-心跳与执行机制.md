# 第 07 章　心跳与执行机制

> 英文原文：`docs/guides/agent-developer/how-agents-work.md`、`docs/guides/agent-developer/heartbeat-protocol.md`、
> `docs/guides/agent-developer/task-workflow.md`、`docs/start/core-concepts.md`。

## 7.1 Agent 不常驻运行

Agent 默认**不是**常驻进程。它们在**心跳（heartbeat）**里醒来——由 Paperclip 触发的短执行窗口。

心跳的触发源：

| 触发源 | 说明 |
| --- | --- |
| **计划（schedule）** | 周期定时器，例如每小时 |
| **指派（assignment）** | 新任务分派给该 Agent |
| **评论（comment）** | 有人 @-mention 了它 |
| **手动（manual）** | 人类在 UI 里点「Invoke」 |
| **审批解决** | 待审批项被批准或拒绝 |
| **依赖解除** | 阻塞它的任务全部完成 |
| **例程触发** | Routines 定时/ webhook / API 触发 |
| **监控到期** | issue monitor 的 `monitorNextCheckAt` 到了 |

也可以接入 OpenClaw 这类常驻 Agent：Paperclip 把它们当外部执行体来协调。

## 7.2 心跳协议

每次心跳，Agent 按固定顺序执行：

```
1. 确认身份        GET /api/agents/me
2. 处理审批唤醒    PAPERCLIP_APPROVAL_ID 存在时先处理审批
3. 取任务          GET /api/agents/me/inbox-lite（或 issues 列表）
4. 选任务          in_progress > in_review（被评论唤醒时）> todo
5. 签出任务        POST /api/issues/{id}/checkout   ← 必须
6. 读上下文        GET /api/issues/{id}/heartbeat-context
7. 干活            用工具执行
8. 更新状态并说明  PATCH /api/issues/{id}（带 comment）
9. 必要时委派      POST /api/companies/{id}/issues（设 parentId/goalId）
```

关键纪律（Agent 侧）：

- **409 绝不重试**：任务归别人了，换一条；
- **不找没派给自己的活**：没任务就结束心跳；
- **只在明确 @-交接时自领**；
- **尊重「发回给我」**：老板说「我来审」，就把任务改回给他并置 `in_review`；
- **执行期内开始干活**，不要只交一份计划；
- **每条进展评论都要写清「已完成什么、还剩什么、下一步归谁」**。

## 7.3 心跳内部发生了什么

```
唤醒队列(去重合并) → 预算检查 → 工作区解析 → 密钥注入 → 技能加载
   → 适配器调用 → 解析输出/成本 → 落库运行记录 → 状态流转
```

- **合并（coalescing）**：短时间内的多个触发会合并成一次心跳，避免风暴；
- **预算检查**：超限直接不唤醒；
- **工作区解析**：找到本次运行该在哪个目录执行；
- **密钥注入**：只注入本次运行被授权的密钥；
- **孤儿运行恢复**：Agent 崩溃后，残留的运行会被自动回收，不留「幽灵占用」。

## 7.4 执行工作区

- **项目工作区**：项目对应的目录（通常是仓库 clone 或 bind mount）；
- **执行工作区**：单条任务的隔离环境（git worktree、operator 分支），任务之间互不污染；
- 子任务**自动继承**父任务的执行工作区；
- 非子任务的后续任务要显式带 `inheritExecutionWorkspaceFromIssueId` 才能续用同一工作区；
- 工作区生命周期与「跨运行持久化」规则见
  `docs/guides/board-operator/execution-workspaces-and-runtime-services.md`。

## 7.5 运行时服务（开发服务器 / 预览）

当任务需要浏览器 QA 或预览服务时，**用 Paperclip 的工作区运行时控制**，
不要自己起没有托管的后台进程：

```bash
GET  /api/execution-workspaces/{id}
POST /api/execution-workspaces/{id}/runtime-services/{action}
```

`action` 包括启动、停止、状态查询等。运行时是**惰性供给**的：没人访问就不会占用资源。
详见 [第 10 章](./10-文档工作区与交付物.md)。

## 7.6 会话与上下文持久化

- Agent 在**同一任务的不同心跳之间保留会话状态**，不会每次从零开始；
- 任务描述 + 祖先链 + 评论区增量构成每次心跳的上下文；
  读上下文优先用 `GET /api/issues/{id}/heartbeat-context`（紧凑、带评论游标），
  不要每次全量重放整个线程；
- 增量读评论：`GET /api/issues/{id}/comments?after={lastCommentId}&order=asc`。

## 7.7 任务工作流建议

一条健康的任务流应该是：

```
todo → in_progress →（产出可检查的东西：PR / 预览 / 报告 / 测试）
     → in_review →（人类或指定评审者确认）
     → done
```

- 进 `in_review` 时**必须有真实的评审路径**：绑定的确认卡片、审批、人类评审者、
  或**真的排期了的** issue monitor；
- 在 `done` 的任务上**不要承诺「我会盯着」**——`done` 就是没有后续；
- 真的需要复查，就设 monitor 并保持 `in_progress` / `in_review`。

设置 monitor：

```bash
PATCH /api/issues/{id}
{ "executionPolicy": { "monitor": {
    "kind": "external_check", "serviceName": "ci", "externalRef": "pr-123",
    "timeoutAt": "...", "maxAttempts": 5, "nextCheckAt": "..." } } }
```

monitor 只在**同时满足**下列条件时才会唤醒：负责人是 Agent、没有用户负责人、
状态是 `in_progress` 或 `in_review`、时间已到。它是**定时轮询**，不是事件订阅。

## 7.8 并行与长任务

- 用**子任务**并行，不要轮询 Agent / 会话 / 子任务 / 进程；
- 委派评审时：让评审 Agent 把结论写在**它自己的评审任务**上并置 `done`，
  不要要求它「把结论发到父任务评论里」（低信任评审 Agent 会被 403），
  然后在父任务上设 `blockedByIssueIds` 指向该评审任务，结论到达会自动唤醒你。
